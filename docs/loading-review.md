# 手機／平板載入檢查（2026-10-10）

## 確認的問題

1. 基準 `abb0dbc` 的首次進入旅路會請求整局圖像，共 11.406 MiB（不含字型、JavaScript、音訊）。四張 HUD 高優先 PNG 共 6,324,328 bytes／6.03 MiB，卻只畫在約 43–220 logical px 的介面上，原圖最長邊 1,254–1,536 px。
2. `ART_READY` 原本只統計封面與 29 張一般圖，未把 HUD 算進去；遊戲也不等待旗標，慢網路下直接繪製程序備援，油耗與敵人照常開始。
3. BGM 4,521,169 bytes（4.31 MiB），長 243.75 秒、約 148 kbps；MAP 2,035,220 bytes（1.94 MiB），長 117.84 秒、約 138 kbps。正式站台支援 `Accept-Ranges: bytes`，無需全檔完成才開始播放。保留原音質，本次未重新壓縮 MP3。
4. 背景音樂原本由 RAF 在狀態轉換後才呼叫 play；主選單另有 120ms 按鈕回饋延遲。這可能錯過手機瀏覽器的使用者播放授權，不是檔案大小足以單獨解釋的問題。已將目標音樂播放移至點擊／按鍵當下，保留尚在載入的播放請求而不立即 pause 取消。
5. 觀察到正式素材快取 `max-age=600`，同批部署的圖像／音訊帶同一發布時間的 Last-Modified／ETag 前綴；原專案沒有持久素材快取。新快取以每檔內容 SHA-256 為鍵，未變素材跨部署重用，不依整站發布時間作廢。這是解決反覆下載的機制，不是所有手機都必定一分鐘的實測證明。

## 改動與量測

| 範圍 | 原本 | 修改後 |
|---|---:|---:|
| 四張 HUD | 6.03 MiB | 0.416 MiB（減少 93.1%） |
| 進入地圖時的圖像請求 | 11.406 MiB | 1.957 MiB |
| 完整地圖＋遊戲圖像請求 | 11.406 MiB | 5.790 MiB |
| 原始 HUD 解碼像素數 | 6,290,436 | 1,867,776（約少 70.3%） |

1. HUD 分發 WebP 最長邊 768px、品質 90、alphaQuality 100；尺寸保持原比例，原 PNG 未覆寫，解碼失敗時仍可備援。不是無損壓縮，已檢視實際手機橫向介面。
2. 旅路先載入自己的九張圖＋封面，遊戲才加入敵人、地形、HUD 與技能；共同素材不重複請求。載入期間顯示圖像進度，玩家輸入與遊戲時間／油耗等待必要素材完成，避免以備援圖直接開局。
3. `service-worker.js` 由 `tools/build-media-cache.cjs` 產生，僅按需快取 196 個已登記媒體路徑，不預下載整包；更新時保留相同雜湊並清掉舊版鍵。HTML／JS 維持正常 HTTP 載入。首次音訊 cache miss 直接回傳完整串流、不等待整首寫入快取；cache hit 支援一般／suffix Range 與 416。
4. Cache Storage 或網路失敗時仍走正常請求；未支援 Service Worker 或瀏覽器清除快取時，仍享有較小 HUD／分批載入，但需重新下載。存檔與熟練度的 localStorage 不變。

## 驗證與限制

1. 核心載入回歸先 RED（5 個失敗）再 GREEN；最終 378/378 Node 回歸通過。新增素材請求去重、HUD 就緒、油耗凍結、同步音樂啟動、跨部署快取重用、內容更新與 MP3 Range；另檢查產生的全部媒體雜湊正確。
2. Windows Chrome 844×390 模擬手機橫向，正式入口 → 旅路 → 第一關，檢查縮小 HUD 與載入完成後的正式美術。這是桌面瀏覽器尺寸驗證，非實體手機。
3. 真實 Service Worker 瀏覽器驗證：查詢參數改變後圖像仍只有一個內容版本快取鍵；MAP.mp3 快取 Range 回傳 206、100 bytes，Content-Range 為 bytes 0-99/2035220。證據見 loading-browser-cache-proof.json 與 loading-cache-smoke.html。
4. 未取得使用者裝置型號、實際網速或 Safari trace，不能宣稱所有手機已縮短到固定秒數。字型 CDN、裝置解碼／記憶體、首次冷快取及音訊自動播放策略仍可能影響體驗；音樂播放授權修補尚需 iPhone／iPad 實機確認。
