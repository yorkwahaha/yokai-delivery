# M15-02 長假名分析

2026-10-15。唯讀 `js/words.js` 公開匯出。未改詞、未改 UI、未讀 `js/audio.js`、`assets/audio/**`、TTS、BGM 或金鑰。音訊 164 包維持凍結。本文件是提案。

## 1. 計數定義

對 `word.jp` 先做 NFC，再逐個 code point：

- 平假名 U+3041–U+3096、片假名 U+30A1–U+30FA：各算 1。小假名（ぁぃぅぇぉっゃゅょゎ、ァィゥェォッャュョヮヵヶ）在這兩個區間裡，算 1，不算 0。
- 長音記號 U+30FC `ー` 算 1。
- 重複記號 U+309D、U+309E、U+30FD、U+30FE 若出現也算 1。這次語料沒有。
- 組合濁點 U+3099、半濁點 U+309A 不算進假名數。NFC 之後若仍留下這兩個碼，另外開清單。這次語料是 0。
- 漢字、拉丁、空白、標點不計。

`kana` 欄與 `jp` 不一致的詞這次是 0，所以用 `jp` 與用 `kana` 同一張表。

現行程式另有 `writtenLength`（`js/game.js:124`）：NFC 之後的全部 code point 數，不排除漢字。`kanaScript`（125-129 行）用 `/[ぁ-ゖー]/u` 與 `/[ァ-ヺー]/u`。小假名與長音在這兩個規則裡也各算 1。組合濁點不在這兩個字元類裡；若字串是分解形，`kanaScript` 會把它當成 mixed。這次 164 詞的 `jp` 都是純假名，所以 `writtenLength(jp)` 與上面的假名數相同。

干擾項不在 164 裡。它們經 `getAnswerCandidates`（`js/words.js:930-931`）可以出現在同一組選項上，所以單獨計數。

## 4. 這些詞出現在哪些文字寬

全部 164 詞都會走上列路徑。假名數 5 的 10 詞與四個干擾項是最寬的一檔。寬度數字是程式常數；沒有用 canvas `measureText` 實測像素。以「一個假名約等於字級」做上限估計時標成推論。

### 到站答題墊

位置：`js/world.js:18-23` 三個墊心 `(h.x-110, h.y+125)`、`(h.x+110, h.y+125)`、`(h.x, h.y+190)`。左右墊心距 220。

圓墊半徑 36，直徑 72（`js/game.js:2780-2816`）。圓在地面層。

假名畫在最上層，直立，字級 33，`fillText`／`strokeText` **沒有 maxWidth、沒有換行**（`js/game.js:3170-3180`，`sceneAnswerFont(33)`）。消除態的墊上是字級 19，同樣沒有 maxWidth（2796-2798 行）。

推論：5 個假名在 33px 下約 165px，會画出直徑 72 的圓，仍小於左右墊心距 220，有機會落在兩墊之間。3–4 個假名也會超出圓本身。這是現役最長詞的實際風險。語料裡沒有假名數大於 5 的詞。

### HUD 任務列

中文詞在任務牌上，`js/ui.js:1610-1613`，字級 18，沒有 maxWidth。

`jp` 加例句只在 `job.showMeaningT > 0` 時出現。`drawHintText`（`js/ui.js:1637`、實作 3171-3186）字級 12，容器寬 `taskW`（1569 行，上限 370），**已經按字元換行**，框高等於行數。這條路徑會保住全部假名。164 詞的例句都不長到需要刪字。

### Boss／破盾題板

`bossQuizLayout`（`js/ui.js:2436-2451`）：題板寬 `min(520, 右界-左界)`，三選項時 `optW = min(152, (w-24-24)/3)`，選項高至少 46。預設 900 邏輯寬、hud 內縮 20 時，左 302、右 672，題板寬 370，`optW` 約 107。

題幹：`zh → jp`（未揭示時 jp 換成 `？`），`fillText` 的 maxWidth 是 `boxW-32` 或有圖示時 `boxW-110`（2499-2506 行），字級 20。

選項：`` `${徽章} ${w.jp}` ``，`fillText` maxWidth 是 `optW-12`（2519-2522 行），`answerFont(18)`。Canvas 的 maxWidth 是橫向壓扁，字高不變。

推論：5 假名加一個數字徽章，在約 95px 的 maxWidth、字級 18 下會被輕輕壓扁。中文題幹通常短於假名。

`readableFont`（3194-3197 行）在 viewport scale 小於 1 時把字級抬到 `min(28, ceil(14/scale))`。`answerFont`（3200-3203 行）上限 31、地板 `ceil(15/scale)`。小螢幕會先變大，再被 maxWidth 壓扁，長假名更容易變扁。

### 單字圖鑑

`drawCodex` 的單字頁呼叫 `CARD_GALLERY_UI.draw`（`js/ui.js:2767` 一帶，資料來自 `wordGallery` 2566-2592 行，即 `getAllWords()` 的 164 詞）。

`writeCard`（`js/card-gallery-ui.js:131-142`）四行：`jp`、`zh`、`kana`、`4/4`（190-193 行）。字級 `clamp(12, floor(step*0.72), 18)`。`ink` 用 `fillText(..., maxWidth)`（120-123 行），同樣是橫向壓扁。

900×600、四欄時卡寬約 215。左右留白各約 `min(卡高比例, 0.27*卡寬)`，文字寬大約 90。推論：字級 18 的 5 假名會貼近這條寬，有機會被壓扁；字級 12 則放得下。`jp` 與 `kana` 現在相同，兩行都是同一串。

同檔 173-174 行的關卡／詞包鈕是篩選標籤，不是這 164 個詞。

`js/ui.js:2668` 與 `2738` 的 `c.jp` 是秘術卡 `CARD_LIST`（かたな、じょうか等），maxWidth 一處是剩餘寬、一處是 108。那不是詞表。以後的字級票不要改到那張表。

### 終局回聽

最多三個記錯的詞，標籤 `jp（zh）`，字級 14（`js/ui.js:2869-2879`）。按鈕 164×44，起點 x = 305 + i*174（469-472 行）。`drawButton` 對標籤使用 `fillText(..., safe.width)`（367-371 行），又是橫向壓扁。

推論：5 假名加括號與兩個中文字，在約 164px、字級 14 下多半單行放得下。壓扁量比答題墊小。

### 誤配名牌

`js/renderer.js:1019-1037`：`jp＝zh`，先 `measureText` 再加寬底板。字級 20。這條已經跟著字串變寬，不刪字、不壓扁。

招牌「神社／魚舖／港町倉庫」是固定標籤（`js/renderer.js:662、714-722`），不是配送詞。

## 5. 提案：保留全部詞與全部假名

不刪詞、不縮短假名、不加新布局模組。沿用已經存在的層。

1. **答題墊。** 圓維持半徑 36。字維持 33，畫在現有的直立頂層，允許画出圓外。只有 `measureText` 寬度大於左右墊心距減去安全邊（墊心距 220，安全邊建議留下後約 200）時，才把字級整數下調，直到整串放進 200。不換行。現役 5 假名按上一節的估計不需要下調；門檻用實測，不用估計上線。
2. **Boss 題幹與選項、圖鑑卡片、終局三鈕。** 拿掉這幾處 `fillText` 的 maxWidth 橫向壓扁，改呼叫已有的 `fitText`（`js/ui.js:3094-3100`）：整字等比縮小到容器寬。字元一個不少，仍然一行。終局鈕高 44、圖鑑一行步進、Boss 選項高 ≥46，現役 5 假名不需要第二行。
3. **若等比縮小會低於該處原本的可讀地板**（Boss 選項是 `answerFont` 在小螢幕的 `ceil(15/scale)`，其餘是呼叫點的原始字級再降兩級），才在**原來的矩形裡**按字元斷第二行。容器不加寬、不新做一層 UI。164 詞在桌面字級下預期走不到這一步。
4. **HUD 詞義。** `drawHintText` 已換行，維持。
5. **誤配名牌。** 已按字寬加長，維持。

以後若出現假名數大於 5 的新詞，同一組規則仍會保住每一個假名：先等比縮小，放不進再在原矩形換行。現在不改 `js/words.js`。
