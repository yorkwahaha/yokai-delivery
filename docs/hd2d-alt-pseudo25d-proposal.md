## 1. 設計摘要

保留現有單一 `ctx`（Canvas 2D）管線，以**一次全域垂直壓縮**模擬俯角，再用一個 helper 讓直立物件「站起來」。

```js
const TILT_K = 0.70;               // 垂直壓縮係數，約對應 ~44° 俯角感（可調 0.65~0.75）

// 世界變換：取代原本 ctx.translate(-cam.x + sx, -cam.y + sy)
ctx.translate(-cam.x + shake.x, (-cam.y + shake.y) * TILT_K);
ctx.scale(1, TILT_K);

// 直立物件：以「實際接地點」為軸心抵銷壓縮，圖像保持原比例。
// 注意：軸心必須明確傳入，不可預設為 obj.y（町屋的接地點是 h.y+46，見下表）。
function upright(pivotX, pivotY, fn) {
  if (!tiltOn) return fn();
  ctx.save();
  ctx.translate(pivotX, pivotY); ctx.scale(1, 1 / TILT_K); ctx.translate(-pivotX, -pivotY);
  fn();
  ctx.restore();
}
```

**接地點（pivot）對照表**（軸心離接地點 d 世界像素，螢幕上會偏移 `d × (1 − k)`；町屋 d=46 → 約 14px 浮空/陷入，且單元測試抓不到）：

| 物件 | 實際接地點 | 依據 |
|---|---|---|
| 玩家 | `P.y` | `renderer.js:51` `drawFrame` 以 `y` 為腳底 |
| 町屋 | `h.y + 46`（排序點 `h.y + 48`） | `renderer.js:523` 接地墨影、`:526` 註解 |
| 妖怪 | `e.y`（刻意不含 `bob`） | `renderer.js:767` 實際繪於 `e.y + bob`，`bob = sin(...)*2`（`:720`，±2px）。軸心固定 `e.y` 會讓 bob 由上下浮動變成約 ±1.4px 的呼吸式伸縮，視覺可接受，**是刻意設計，勿改成 `e.y + bob`**（會引入抖動）。其他含 offset 的怪物型別【待逐型驗證】 |
| 石燈 | `l.y + 8` | `game.js:2363` `drawScenerySprite(lamp, l.x-lw/2, l.y-lh+8, lw, lh)`，底邊 = `l.y+8`。`lampLightY = l.y-22`（`LAMP_LIGHT_LIFT`）是光心，與接地無關，勿混用 |
| 靈玉、貨物、鳥居、櫻樹 | 【Stage 2 逐一對照繪製函式的底邊/接地墨影後填入】 | |

```js
upright(h.x, h.y + 46, () => RENDERER.drawHouse(h));      // 町屋
upright(P.x, P.y,      () => RENDERER.drawPlayer(P, …));  // 玩家
```

關鍵性質：
- 貼地層（地面、道路、答題圓墊、神域曼荼羅、焦土、Boss 預警地場）**零修改**即自動變成斜視橢圓（僅限未預壓扁者；已含 `SQ=0.6` 等的素材見 §5.13）。
- 直立物件（角色、怪物、町屋、標記）用接地點 `upright()`；原有高度常數原則上不重算，但浮動標記應按宿主接地點投影（§5.14），不可對同一高度重複補償。
- 全程單一 `ctx`、原圖層順序不變，夜色遮罩前後（原 2807 註解契約）不受影響。
- `drawStyledSceneryImage`（`renderer.js:328-341`）使用 `ctx.filter`；在 `upright` 內圖像未縮放故無影響，Stage 1 截圖時順帶確認不在世界變換內的景物沒有模糊強度差異（1/k 倍）。

## 2. 單一路線與保留的工程契約

**只修改 Canvas 2D 戰鬥世界投影**：不新增 WebGL、雙畫布、GLSL、GPU Chunk 快取或 24 層 GL 佇列。旅路地圖、選單及 HUD 維持原管線。

保留前期審查中仍適用的要點：

1. **既有圖層契約**：`FX.drawGround` 在角色前；夜色 `renderLighting` 在自發光 `FX.draw` 與刀氣前；`game.js:3405` 黑龍在 HUD 後、標題牌/Boss 面板前。保留 `actors.sort`、飄字區段與測試字串錨點，不擅改順序。
2. **光照數學語意**：主角漸層內圈 15px、石燈漸層內圈 10px 為固定平台；保持 `destination-out` 挖光、`lighter` 暖光、`lampout` 油量與燈滅語意。投影後須驗證光池位置、形狀、中心透光率及光圈邊界，不能只憑肉眼覺得「有亮」。
3. **相容性與畫布生命週期**：沿用唯一 `canvas#game` 與 `alpha:false`、既有 backing store / DPR / 搖桿與觸控。載入順序維持 `fx.js → skillfx.js → game.js`、`boss-ai.js` 在 `game.js` 前；世界變換不得滲入選單與旅路地圖。
4. **品質與效能驗證**：Node 契約測試之外還要有瀏覽器截圖、投影幾何/文字對位測試、重烘焙統計、P95 幀時間、平板/手機實機驗證。沿用既有減少動態與行動裝置 DPR 策略，不引用其他架構的 VRAM/FPS 估算承諾。

**決策門檻**：只先做 Stage 0 → Stage 1 的可回退原型；未讓視覺更有縱深則停止。

## 5. 需解決的具體問題

1. **烘焙貼花被壓扁**：`drawStaticChunk` 的鳥居（`:375`）、櫻樹（`:384`）及區名（`:369–374`）需自地形快取移出；鳥居/櫻樹按直立實體排序，區名改螢幕正交字體並保留原層序。
2. **可視範圍變大與世界剔除（相機常數為渲染錯誤，非平衡項）**：
   - **相機（必改·渲染錯誤）**：`game.js:2202` `targetCamY = P.y - H / 2` 在 `screen_y = (y - cam.y) × k` 下，主角落在 `(H/2) × k`＝35% 高度（k=0.70），整局偏上。必須改為 `P.y - H / (2 * TILT_K)`（`:2201` 的 X 不變）。
   - **世界剔除範圍**：垂直方向可見世界範圍為 `1/k` 倍。`viewBounds()`（`game.js:27`）回傳的是 `viewport.js` 的邏輯螢幕矩形，**但它同時被螢幕空間用途使用**，不可在其內部統一 `/k`：
     - 世界座標用途（需 `/k`）：`:1403`（妖刀波）、`:1608`、`:1624`（精靈）、`:1723`、`:2342`→`nearView`（町屋/敵人/LAMPS/彈幕剔除）；
     - 螢幕空間用途（**不可改**）：`:2216`（雨）、`:2234`（霧漸層）、`:2878`（Boss 標記 `sx/sy` 螢幕判斷）、`:3363/3372/3392/3428`（HUD/封面/UI）。
     - 做法：新增 `worldViewBounds()`（回傳 `{left, right, top: top / TILT_K, bottom: bottom / TILT_K, …}`，相對 cam 的世界偏移），僅替換上列世界用途；`renderer.js:131 bounds()` 同樣有世界/螢幕混用，拆法見 §5.8。漏改會讓「在畫面上的東西被剔除」（整批消失），需以 `rg viewBounds\(` 全數核對並於 Stage 1 加入計數檢查。
   - **平衡決策（更正：前版「縮小 view 維持平衡」不完整）**：螢幕尺寸固定時，無法同時保持兩軸的可視世界範圍。選項：
     - (i) 接受垂直可視世界變 `1/k` 倍（約 +43%），水平不變——敵人更早可見，需重新平衡生成環/預警；
     - (ii) 整體等比放大 `1/k`，垂直可視世界不變，但水平可視世界縮為 `k` 倍（約 −30%），側向敵人較晚可見；
     - (iii) 折衷：放大 `1/√k`（`k=0.70` 時：水平可視世界約 −16.3%、垂直約 +19.5%）。
     - **選項 (ii)/(iii) 的副作用**：世界整體放大 `Z>1`，所有 billboard 在螢幕上同步放大，每個 texel 攤到更多螢幕像素，有效貼圖解析度下降、浮世繪筆觸變軟；且 HUD 在螢幕空間不縮放，會出現「世界變大、HUD 不變」的比例差。原型時須特別檢視。
     - Stage 1 原型以截圖與實玩決定；在決定前，生成環、危險區預警、送達距離判定均不得改動數值。
3. **輸入座標**：`pp()`（`game.js:3054-3060`）回傳的是**邏輯螢幕座標**，其呼叫點（`:3079/3085/3208/3218/3223/3227`）皆為搖桿、按鈕、選單等螢幕空間 UI，HUD 不經世界變換，**`pp()` 不可加 `/ TILT_K`**。目前未發現「指標 → 世界座標」的用法；若日後加入，才用 `screenToWorld`（`y = cam.y + sy / TILT_K`）。**所有世界座標距離判定（答題圓墊選取 `:2185-2188` 的 `dist(P,p) < 38`、命中、剔除）維持原值，絕對不可除 `TILT_K`**——世界圓在壓縮下自動成橢圓，視覺與判定同源同變。搖桿方向沿用螢幕向量，但世界位移的垂直分量是否以 `/k` 補償視覺速度，需另行決策（見 §7）。
4. **光照：光心座標壓縮 + 橢圓化（阻擋級，移動時才會顯現）**：`renderLighting`（`game.js:2800`，在 `ctx.restore()` 之後）是**螢幕空間**，光心以未壓縮的世界差值計算：`renderer.js:939-940`（`screenPx/screenPy`）與 `:958`（石燈 `lx/ly`，含 `LAMP_LIGHT_LIFT`），以及同函式內暖光（`lighter`）段落使用相同光心的位置。開 tilt 後必須：
   ```js
   const screenPy = (P.y - camY + offset.y) * TILT_K;
   // 石燈整支直立（軸心 l.y+8），火袋在軸心上方 8+LAMP_LIGHT_LIFT = 30px：
   const ly = (l.y + 8 - camY + offset.y) * TILT_K - (8 + LAMP_LIGHT_LIFT);
   // 〔更正〕前版 (l.y - LAMP_LIGHT_LIFT - camY + off) * k 在 k=0.70 時比正確值低 30·(1−k)=9px。
   ```
   不改的話，光斑垂直偏移 `|P.y - camY| × (1 − k)`：畫面中央偏移為 0，**靜止時看不出，一移動光池就與角色脫節**。`offset.y`（震動）同樣乘 `k`，與世界變換 `(-cam.y + shake.y) * TILT_K` 一致。橢圓化須**圍繞各光心**：`translate(cx,cy) → scale(1,k) → translate(-cx,-cy)` 後再填漸層，直接 `scale` 會讓光斑整體上移。`:959` 的視野外裁剪使用已壓縮後的 `lx/ly`，不需另改。
   - **油量視野（已決策：保持 `×k` 橢圓，即選項 b）**：螢幕上橢圓 y 半軸為 `baseRadius × k`，而地面也同比壓縮，故對應的**世界圓半徑仍是 `baseRadius`**——視野的世界範圍與數值（油量）完全一致，並非「少 30%」。選項 (a)（y 半軸 `baseRadius / k`）反而會讓世界視野在垂直方向放大為橢圓，改變遊戲公平性，不採用。驗收：Stage 3 以截圖確認光池邊緣與同距離（世界圓半徑）的地面標記對齊；`lampout` 判定（`game.js:919-926`）與油量邏輯不動。
5. **震動採樣**：同畫格世界、`renderLighting` 及 HUD 上層黑龍共用一次 `getShakeOffset()`；不可由 `drawDragonHudOverlay` 再獨立抽樣。
6. **碰撞/命中視覺一致性**：邏輯仍在世界平面圓上，斜視後命中環/範圍自然為橢圓，視覺正確；直立判定框不變。
7. **`ctx` 之外的離屏繪製**：`FX.glow`、`SKILLFX`、`drawSlashArcs` 等使用世界座標，需逐一確認不依賴「圓形必須為圓」的語意。
8. **【阻擋級·已驗證】地形快取覆蓋不足**：`renderer.js:467-468` 以 `area.height + 240` 決定快取高度，並於 `:508` 在世界座標 blit。CTM 含 `scale(1,k)` 後，`t.height` 世界單位只覆蓋 `k×` 螢幕高度，畫面下緣約 30% 會沒有地面。必須改為 `ph = ceil((area.height / TILT_K + 240) * pixelScale)`，`:461-462` 的 `movedBeyondCache` 同步以 `/TILT_K` 擴張。**不可直接擴張 `bounds()`**（`renderer.js:131`）：它有 7 個呼叫點，世界/螢幕各半——世界用途（需 `/k`）：`:440`（`drawGroundBase` 地形快取）、`:1183`（`drawGroundParallax`，於 `game.js:2351` 世界變換內呼叫，內部 `worldLeft = cam.x + area.left - 100`，容易漏看）；螢幕用途（**不可改**）：`:168`（`lightCv` 尺寸）、`:295`（粒子 cull）、`:923`（`lightCv.clearRect`）、`:1209`（`drawMistParallax`）、`:1236`（`drawAtmosphere` 粒子播種）。做法：新增 `worldBounds()`，只供 `:440` 與 `:1183`，`bounds()` 原封不動。**`height` 也必須一併除 `k`**：`:468` 的 `ph = ceil((area.height + 240) * pixelScale)` 讀的是 `area.height`（`viewport.js:14` 的 `v.height`），不是 `bottom - top`；只改 `top/bottom` 會讓 `ph` 短約 30%，畫面下緣仍無地面（正是本節要防的 bug）：
   ```js
   const worldBounds = () => {
     const a = window.VIEWPORT?.bounds();
     if (!a) return { left:0, top:0, right:W, bottom:H, width:W, height:H };
     const top = a.top / TILT_K, bottom = a.bottom / TILT_K;
     return { left: a.left, right: a.right, top, bottom, width: a.right - a.left, height: bottom - top };
   };
   ```
   `game.js` 的 `worldViewBounds()` 比照辦理，保持 `width/height` 自洽。`:1183 drawGroundParallax` 的 `cloudParallax = 0.20`（`renderer.js:1186`）是螢幕空間視差係數，是否隨 `k` 調整為獨立小決策，不影響正確性，Stage 2 目視決定。否則未開 tilt 時也會改變霧/粒子外觀。已確認不受影響的部分：`:474/484` 以 `setTransform` 自行重設烘焙（不會二次壓縮）；`:441` 的 `getTransform().a` 取 X 縮放，只縮 Y 不影響像素對齊；`game.js:2586` y 排序為純世界空間。
9. **螢幕空間圖層不在世界變換內**：`game.js:2851` `ctx.restore()` 之後，`drawMistParallax`（2855）、`drawAtmosphere`（2859）、`drawStageWeather`（2860）在螢幕空間以 `cam` 手算座標（`renderer.js:1189/1220`）；敵方火彈（2863-2870）與 Boss 追蹤標記（2874-2893）也在 restore 後各自 translate/手算 `sx,sy`。它們不會跟地面壓縮，需明確決策：
   - 霧/雨/櫻花/幽火（環境粒子）：維持螢幕空間，不壓縮，只將內部 `cam.y` 視差運算視需要 `×TILT_K`，使移動時與地面同速；
   - 敵方火彈：改為套用世界變換（含 `TILT_K`）並對彈體 `upright`，否則與地面錯位；
   - Boss 標記：`sy = (bossTarget.y - cam.y) * TILT_K`。
10. **震動採樣不只兩處**：除 `drawWorld` 的 `:2331` 與 `:2800` 外，`drawDragonHudOverlay`（`:2898`）有第三次獨立採樣。改為每幀取一次並以參數傳入（或存於模組變數）。

15. **陰影是否跟地面壓縮需看美術**：町屋 `renderer.js:523`、主角 `:645`、妖怪 `:764` 原本的接觸陰影已手調為扁橢圓。整個函式包 `upright` 會保留比例；拆成貼地圖層則又乘 `k`。Stage 1 預設不拆，同場景比較兩版本。若拆，保留各陰影中心的原始相對偏移（町屋 `h.y+46`、玩家 `P.y+22`、妖怪 `e.y+0.85×r`），**陰影中心不等於角色 upright pivot**，不能直接強制改為腳底。
16. **移動手感**：Y 軸視覺速度乘 k，Stage 1 不改移動、生成、攻擊距離或敵人追擊數值，先實玩。
