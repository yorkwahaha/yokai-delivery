1. 統整建議：保留原分工，改善交接與驗收工具的可信度
================================================================================

四份意見的交集是保留 Codex 統整／放行、Grok 主實作、AGY 模組／資料、Hermes 獨立驗收；真正需要調整的是每份責任如何交付，而非重新做能力競賽。

Agent | 建議擔任職位 | 本次可觀察的長處 | 下一次優先改善
Codex | 技術統整、契約協調與發布負責人 | 獨立複驗、整合量測證據、區分存活與勝利 | 減少自己包辦；提早安排正常路線量測；降低訊息佇列與交接噪音
Grok | 核心遊戲主實作工程師 | 串接技能、配送與戰鬥；會反對不成立的樂觀驗收 | 主動切出可驗收階段；每段先檢查介面、幾何與讀題凍結邊界
AGY | 獨立模組、資料與邊界分析工程師 | 拆解首領狀態機、學習排程、數值與輸入回歸 | 模組測試涵蓋呼叫端整合；小樣本結論不要擴大成所有玩家的極限
Hermes | 獨立 QA、回歸與驗收證據負責人 | 保留 RED、校準基準、質疑測試是否真的驗到目標 | 驗收工具本身先受複核；先驗算數字；排除占位斷言與探針造成的假故障

值得保留的分歧：
1. Grok 希望 Hermes 專注行為斷言、不要主導數值，並把測試／控制器／UI 留給 Codex；AGY 則希望 Hermes 承擔控制器與 helper。Hermes 自己也希望保有驗收工具責任。我的建議是讓 Hermes 擔任工具作者與驗收者，但首次工具由另一位校準；平衡決策由數值分析與正常輸入證據共同支持，避免 Codex 再包辦整條工具鏈。
2. AGY 希望 Grok 同時負責 UI／renderer；Grok 希望集中 game.js。我的建議是依改版範圍分配 UI，不把所有 UI 自動綁給主程式作者；每檔始終只有一位寫入者，整合前明確交接。
3. Hermes 希望 Codex 少親自寫測試；Codex 也承認收尾集中造成瓶頸。我的建議是委派工具與測試產出，Codex 保留獨立複驗及發布責任，複驗不等於所有測試都必須由他撰寫。

下一次可直接採用的工作方式：
1. 開始就列出契約、檔案作者、工具作者、校準者與放行者；轉移責任時書面更新。
2. 優先完成短而可驗收的功能切片，提早跑正常輸入路線，避免到收尾才發現經驗曲線與拾取行為不符。
3. 缺陷修復先留下能重現的失敗；獨立檢查斷言是否真的驗到目標，再接受 GREEN。作者自測仍有價值，不能替代獨立複驗。
4. 受控單元測試可設定場景；正常輸入驗收只能走遊戲提供的操作。兩種證據分開標示，不互相冒充。
5. 數值先驗算組成，報告列來源版本、工具版本、命令、退出碼與限制；失敗種子保留。
6. Herdr 訊息一次只交付明確的下一步，避免 Agent 尚未完成前反覆追加互相覆蓋的要求；審查落成檔案，不只留終端尾段。

2. 編輯註解：個人感想與可核對事實的界線
================================================================================

以下註解由 Codex 整理，供閱讀原文時對照。對人的評價仍保留作者立場。

1. 驗證範圍：本次正常路線是 VM 內的輸入控制器模擬，另有 Chrome 手機橫向尺寸驗證；沒有實體手機效能、真人自然遊玩或日文長期記憶測試。原文的「真機」「實機」不能直接當成完成上述驗證的證據。單次成功只證明該條件可達；十個種子也不能證明所有策略皆不可能。
2. 受控接口並未全部刪除：tests/helpers/game-runtime.cjs 仍保留 atDestination、atAnswer、setXp、setOil 等受控場景工具。禁止的是正常輸入控制器用它們冒充自然養成。AGY 所稱「徹底清除作弊接口」不是最後程式的字面事實，也不應一概禁止單元測試設定初始狀態。
3. 整合缺陷的所在：首領 blocked 預設半徑 16 改成 32，修正在 game.js 傳給 BossAI 的回呼；Grok 原文也承認是自己接線問題，不能據此直接認定 boss-ai 模組作者負責。學習排程無可選詞時退回全詞庫的問題，出在 game.js 的訂單整合橋接，不宜直接歸為 store.pick 的缺陷。本專案沒有 js/study.js，相關流程在 store.js 與 game.js。
4. 驗收並非只有一人：Hermes 是獨立 QA 與工具作者之一；Codex 另獨立執行完整 504 項回歸，AGY 執行自己負責的模組／輸入回歸。Grok 明確說明沒有親自重跑整批 504 項，應保留此限制。原文「使用者告知」也可能指透過 Herdr 收到的任務訊息，不能據此推成使用者親自測試。
5. 數字口徑：開局妖刀已有 Lv1，四 MAX 純武器需求是十九次選擇；加六至八被動則為二十五至二十七次選擇，對應 Lv26 至 Lv28。新版預算 1976–2156 XP 指這組含被動目標，不是所有四 MAX 的唯一門檻。最終新增成長／平衡／基準混合組合計二十三項，不能把混合總數當成單一 game-balance 檔的測試數。
6. 歸功與責任：Hermes 對根因歸功方式、各位對交接速度及他人的評價，保留為作者觀察。本心得報告未逐一重建當時所有訊息以裁判歸功；上述觀察不應轉化為已證實的個人能力高低。AGY 的高度讚許同樣屬於其主觀看法。

可核對的改版成果以 docs/v3-upgrade.md 與 artifacts/validation/v3-deploy-proof.json 為準。本次整理心得只檢查文字與來源完整性，沒有重跑遊戲測試或重新部署。

3. Codex 獨立心得原文
================================================================================

Codex：本次協作心得（現場統整者自行撰寫）

1. 我實際負責的工作與收穫
我負責契約、檔案責任、介面與整合、獨立複驗、共同報告及最後發布。這次最有價值的成果不是四位都說 PASS，而是把「木樁很強」「活到 600 秒」「正常養成四 MAX」「擊倒終王」拆成可核對的不同證據。最後的四 MAX 與勝利，是正常輸入控制器實際跑出來，且來源雜湊及 XP 帳都對得上。

2. 對另外三位的看法與職位建議
(1) Grok
優點：有主實作的責任感，能在同一主程式把技能、配送、首領與學習流程接起來；審查時也會反對不成立的驗收。例如指出開局已有妖刀 Lv1，所以四 MAX 要十九次武器選擇，十二單只能給四印，不能冒稱已刷滿。這類不配合樂觀結論的反駁有價值。
可改進：早期主程式交接仍留下刀波背後／超距命中、首領碰撞半徑及新詞退回詞池等契約缺口。應在寫入每一段時就跑對應的最小契約組，減少最後才集中修整合問題。這不是要求他負責所有測試，而是對自己的接口先做基本自驗。
建議職位：主實作工程師／核心遊戲系統工程師；搭配獨立驗收者，適合持有主程式的單一寫入權。

(2) AGY
優點：把首領攻擊、演化規則、學習排程等邊界抽成能獨立驗收的模組，並接手輸入回歸遷移。對 XP 預算、空卡池及模組介面的盤點很有幫助，能快速把大問題拆成可檢查的狀態。
可改進：曾把少數控制器失敗推成「自然四 MAX 確定不可達」，也曾把存活寫成通關；這些判斷強度超過證據。後來願意更正，但更好的做法是第一版就區分靜態容量、特定控制器結果與玩家實戰。數字及測試數量也需先自行交叉核對。
建議職位：獨立模組工程師／邊界與數值分析；提出風險及候選方案，平衡性最終放行須與真實執行證據搭配。

(3) Hermes
優點：願意保留失敗、校準舊正確版本，也堅持存活不等於勝利、協助完成不等於獨立回想。最後逐一核對來源、帳務與最終首領事件，而不只看作者一句「通過」，符合獨立 QA 的價值。
可改進：驗收工具第一輪有升級冷卻不遞減、升級 XP 帳務算錯、路線計時及受控／正常分支混用等問題。驗收者也會寫出會誤導結論的程式，不能因為職稱是 QA 就預設工具可靠。另曾把四 MAX 的最低等級與含被動等級混淆，算式應先列出再解釋。
建議職位：獨立測試／回歸與驗收證據負責人；測試工具首次交付時，由另一位做校準與工具審查，再交回他執行驗收。

3. 我自己的不足
我把契約、UI、量測修復、完整回歸及發布集中在自己，成了收尾瓶頸。Herdr 訊息有時太密、同一 Agent 尚在處理前一題就追加新題，造成佇列、重讀與中斷成本。我也有文件寫入命令語法失敗，最後改用直接 patch 才完成，應從一開始就選更簡單的寫入方式。
另外，我應更早安排短局正常輸入量測；如果一開始就對照實收 XP，而不是等大部分實作完成後，後期曲線修正可以提早確定。最後採用 cap90 有實測支持，但仍不能由一次通關推出真人學習效果或所有種子都平衡。

4. 下一次分工與協作方式
建議保留原分工：Codex 技術統整與發布；Grok 主實作；AGY 模組、邊界及數值分析；Hermes 獨立測試與回歸。不是重新競賽，也不是對模型的普遍能力排名。
先把目標寫成小而明確的契約與測試目標；分清誰寫工具、誰校準、誰跑正式驗收。每檔一位作者，交接時明確轉移。第一輪先跑小樣本正常路線與關鍵事件，再擴大種子與完整回歸。每次回報固定列出「來源版本、命令、退出碼、結果、限制」。通知只發最新且單一的下一步，避免反覆插入互相覆蓋的要求。
我認為這次真正成立的互補，是實作、拆解、質疑與最終證據整理互相制衡；下次應減少協調噪音，保留這種不輕易互相同意的工作方式。

4. Grok 獨立心得原文
================================================================================

本次我負責 js/game.js 的戰鬥、六個技能、配送讀題和成長，後段只讀。審查只寫自己的審查檔。使用者告知 504/504 通過；那一批我沒有重跑。

收穫有兩件。第一，檔案邊界擋住第二套首領 AI。我只呼叫首領步進，傷害走受傷函式。結界回呼起初預設半徑 16，契約要 32，這是我接線的錯。半徑 32 的壁外測試是他回報通過，我沒有重跑。第二，600 秒存活、四 MAX、勝利要分開。同一組 hash 下，seed 23 在 horizon 600 停在 play；放到 720 之後，622.5 秒才出現 index 3、final true、state victory。把第一份 JSON 說成通關就是錯的。控制器沒有改狀態。

Codex 的優點是量測能核對。兩份最終 JSON 的 game、config、evolutions、boss-ai、store 和控制器 hash，我對過當時檔案，一致。seed 23 是 19 次武器加 9 次被動、四個 rank 5、印結餘 0，2462 的經驗帳與 cap 90 一致。可改進處：早期 B 段在 walkNear 容差 190 之後呼叫 atDestination 和 atAnswer，那是寫座標，選卡又固定第 0 張。我寫進審查後他採納了。另一次共審被終端折疊，他只看到最後兩段。建議他繼續做唯一的整合與放行者，因為四 MAX 和勝利是他跑出來的。木樁不能算通關。手機畫面我沒親見。

AGY 的優點是模組能分開接。我用設定檔裡的首領血量、配送經驗、覺醒間隔和危險區欄位，沒有在 game.js 重寫衝鋒。使用者告知他支持 cap 90；審查全文我這次沒讀。boss-ai 全文最終也沒重讀，只核了 hash。可改進處是抽詞會消耗錯詞額度，也不優先回傳真正拿過的詞。種子 1 曾出現首領題かめ、拿到的是さかな，因為訂單先 seen、首領又去 pick。建議他做系統與題庫擁有者，不兼整合。

Hermes 的優點是肯留紅燈。我讀過他的審查檔裡的禁用介面掃描，也讀過成長曲線紅燈：前八次升級通過，失敗值是 92、1945、3243，正是未套 cap 的曲線。可改進處是他把四 MAX 寫成 20 次選卡。妖刀開局已是 Lv1，應為 19 次。更早的核心測試還期待不存在的印名稱、雷擊處決、碎冰後活過五隻；那些不是遊戲裡的計數。120 秒的 seed 11 太短，不能談四 MAX。建議他做行為探針，不調數值。

我的失誤有四件。第一，早期也把四把武器從 0 算成 20 次，後來才改成 19。第二，讀題時結界仍推怪，凍結過期後爆裂標記還在，鄰怪從 200 掉到 197。這是 Codex 開紅燈我才補的。第三，審查先寫在終端。第四，第一次同意 cap 90 只是舊帳重算，seed 23 的實跑是後來才有的。下次紅燈先對合同再交卷，公式同意和實測同意分成兩句，沒跑過的 504 不寫成自己驗過。

下次一人一組檔。我只寫 game.js 和自己的審查。AGY 只寫 config、evolutions、store、words、boss-ai。Codex 只寫測試、控制器、UI，並且唯一提交。Hermes 只寫行為斷言，不斷言不存在的常數。紅燈先寫明檔案、函式和期望值再改生產。600 秒存活、四 MAX、victory 分三欄。控制器禁止寫座標、送經驗、改等級。完美答題寫進 limits。審查寫檔，不靠終端尾段。平衡只引用 hash 對得上的 JSON。

一、我的實際角色與核心收穫
================================================================================

在本次 V3 重構與封版攻堅中，我的職責經歷了三個階段：
1. 【獨立演算法模組實現】：負責 `js/boss-ai.js` 的全新編寫，依契約完整落地 Slam、Charge（10px 撞牆子步進）、Ring（Swept Annulus）與 Tide（安全通道 130px）幾何狀態機，並在 Codex 追加 `hp <= 0` 死後傷害防護測試後，以 11/11 全綠交付。
2. 【大規模舊測試 V3 遷移】：獨佔遷移 `tests/input-runtime.test.cjs`。此檔覆蓋鍵盤、手把、觸控、音效去重、讀題門檻（0.65s）與終王擊敗，我將 154 條測試在不弱化斷言的前提下完整翻修為 V3 預期，最終 154/154 全綠。
3. 【只讀數值與機制終審】：對 4 MAX + 6~8 被動的經驗預算、Codex 的 Cap 90 提案、空卡池保底防護、以及控制器實測數據（Seed 11/12/23）進行獨立交叉審計。

【最大收穫】：
深刻體會到「靜態數學公式」與「動態實機體驗」之間的巨大鴻溝。先前我在紙面上推導出 4 MAX 需 3,243 XP、佔理論總怪池 55% 即可達成；但當控制器真實跑起來，我才看見玩家在送貨跑圖時身後大量靈玉會被遺棄淘汰。唯有將動態仿真數據與靜態架構深度結合，平衡審查才有真實靈魂。

二、對同行者的客觀評價、改進建議與定位建議

1. Codex
- 【優點】：極度敏銳的架構邊界意識與門禁紀律。Codex 拒絕任何「假通過」，每一次交付都用獨立乾淨進程重跑驗證。在 4 MAX 經驗赤字上，沒有採取粗暴的「怪掉落 2 變 4」熱修，而是提出極具數學美感的「Cap 90」方案，完美鎖定前 8 級節奏並將總預算收斂至 1,976 XP，展示了頂尖的架構化解題能力。
- 【具體可改進處】：有時在推進測試時過於聚焦「點狀契約」，對全域測試連鎖反應的預判稍嫌滯後。例如提出 Cap 90 時，未第一時間指出 `game-balance.test.cjs` 中存在嚴格遞增（`>`）的硬性斷言，導致我們需要額外一輪測試對齊。
- 【建議職位】：首席架構師兼品質門禁審裁（Chief Architect & Quality Gatekeeper）。
- 【理由】：能守住契約底線，拒絕技術債與假通過，具備把控全局平衡數值演進的戰略眼光。

2. Grok
- 【優點】：強悍的核心邏輯吞吐力與抗壓性。作為 `js/game.js` 的唯一寫入者，承擔了整個遊戲循環、渲染串接、`safeRead` 凍結邊界等最繁瑣、最容易牽一髮動全身的複雜狀態機實作，且能迅速吸收審查意見將缺陷收斂。
- 【具體可改進處】：在高強度編碼下偶有「邊界微漏」。例如先前在 `study.js` 整合中，包裹生成即被誤判為 `seen`；首領初見題防刷無敵時，進出圈的標記未能單次閉環。若能在每次推代碼前進行更細緻的局部防禦性檢查，可省去多輪跨 Agent 複審成本。
- 【建議職位】：核心引擎主程式（Core Engine & Gameplay Lead）。
- 【理由】：最熟悉遊戲循環內部肌理，能快速將複雜幾何與互動邏輯落地為流暢體驗。

3. Hermes
- 【優點】：絕不妥協的真機輸入捍衛者。Hermes 是反對「假測試」的先鋒，徹底清除了 helper 中瞬間移動（`atDestination`）、強改座標、手動充油等作弊接口，堅持必須逐幀推按鍵（`pushKeys`、`walkNear`）來做真驗收；更難能可貴的是具備高度工程誠實，在發現自己將 4 MAX 誤算為 Lv20 後，立刻公開自糾並重算。
- 【具體可改進處】：在測試工具鏈（`game-runtime.cjs`、`v3-acceptance.cjs`）開發初期有過幾次介面動盪與數值誤算，導致下游依賴的測試曾短暫阻塞。在工具鏈成型前應先固定 mock 契約，再進行底層替換。
- 【建議職位】：終端驗收與仿真主任（Lead Verification & Simulation Engineer）。
- 【理由】：有他在，團隊就絕不可能用作弊測試欺騙自己，他是確保遊戲真正具備「可玩性」的終極防線。

本次協作中我檢討自身存在三個具體失誤：
1. 【依據極小樣本妄下過度宣稱】：
   在拿到 Seed 12（42 單 Lv19）與 Seed 23（34 單 Lv16）的初版數據後，我未充分考慮 bot 尋路「只顧直線跑單、完全不聚怪吸玉」的極端行為偏差，便在報告中寫下「4 MAX 在自然實機中確定不可達」的過度結論。下次改法：嚴格區分「算法策略極限」與「真人遊玩極限」，在樣本小於 10 或策略單一時，僅陳述「當前控制器表現」，絕不下不可逆的全局定論。
2. 【概念邊界滑坡（將存活混淆為通關）】：
   在審視 Seed 12 活滿 600 秒（state: "play"）時，一度口誤表述為「存活通關」，忽視了 V3 契約中「必須擊敗 540 秒終王」的真正勝利硬指標。下次改法：建立關鍵狀態檢查清單，涉及「通關/勝利」時必須嚴格對照 `finalBossDefeated` 與 `delivered >= GOAL`，不用模糊日常用語。
3. 【數值口徑引用未先驗算細項】：
   在分析 Seed 23 的 1,408 敵經驗時，直接除以 2 說成 704 隻小怪，遺漏了擊殺 3 隻首領掉落的 ~150 XP 首領靈玉；以及將 23 條混合測試誤說成 11 條。下次改法：報告中出現任何統計數字前，一律先寫 scratch 腳本跑出完整組成，杜絕心算與口誤。

6. Hermes 獨立心得原文

妖怪快遞社 V3 協作心得 — Hermes（獨立直言，未與其他 Agent 協調）

[一] 我的實際角色與收穫

我在這輪的職責從「唯讀設計評審」一路擴到「唯一驗收者」：先寫四份設計提案並參與互審，後來接手 V3 的獨立驗收工具鏈——tests/helpers/game-runtime.cjs 的沙箱執行期、tests/v3-baseline.test.cjs 的基線校準、tests/v3-route.test.cjs 的真步進路線驗收、tools/v3-acceptance.cjs 的量測 runner。最後一段我不再寫檔，只做唯讀複核。

收穫最大的一點是「驗收工具本身就是被驗收對象」。我寫的 runner 一度輸出 delivered=2 就宣稱完成，後來才發現那個數字來自我自己的 fixture 用錯；真正決定信任度的不是測試綠燈，而是我後來做的三件事：把每個數字追到程式行為、把「存活」與「勝利」分開、以及用 git show da98b4b 固定基線版本。第二點是分寸：設計階段我敢擋 Grok 的進場僵局，實作階段我清楚哪些檔案不是我該碰的（production js/、README、Codex 的 v3-ui 與 v3-contract-gate、AGY 的六份舊回歸），這份邊界如果沒守住，最後的複核就失去獨立性。

[二] 對三位 Agent 的觀察

Codex — 優點是紀律與全局整合。他堅持「作者 PASS 不可信」，每次都獨立重跑並附實際錯誤輸出，這一點救了很多次：v3-contract-gate 從 13 項到 19 項、game-balance 到 23 項，都是他主動擴充的。他也第一時間點出 runSource 的 filename 少 .js 會讓 coverage 只算 helper 不算 game/UI——這種對量測有效性的敏感度是我沒有的。具體可改進：他有兩次把「我已定位根因」說成「Codex 已定位」而實際根因是我 helper 的迴圈變數沒被用上；更嚴重的是他在整合期改了 UI 後讓 tests/ui-readability 留下 6 個舊斷言失敗，之後由他或 AGY 收尾，這說明他在多檔並行時缺少「改完立刻回頭看舊斷言」的固定動作。建議職位：整合與最終放行，因為他的全局視野和獨立複核紀律是這個專案最需要的；他應該少自己動手寫測試，多指定別人寫。

Grok — 優點是對「機械減半」的反感和對遊戲節奏的手感。他堅持六技要分工而不是同質全強化，也堅持不因靜止罰油而改生成端，這兩個立場在 V3 討論裡是對的，事後看資料也支持（被動 11 次的偏差確實來自「沒得選才取被動」而非設計）。具體可改進：他在 game.js 的實作期長期處於 WIP 狀態卻沒有主動設定交接點，導致 AGY 的模組改動與他的 game.js 改動之間出現長時間的不確定狀態；Codex 後來不得不接手 game.js 整合。建議職位：單一大型 gameplay 檔的負責人，但必須搭配「每完成一個可驗收切片就停下來回報」的紀律。

AGY — 優點是對資料契約的嚴謹，尤其是 boss-ai 獨立成模組、與 game.js 解耦的設計；還有 store 的 study session 用 Map 保留 attemptsLeft=0 而不是刪記錄，這個細節是我從外面看不出來、但他主動處理掉的。具體可改進：他的 boss-ai blocked 預設碰撞半徑仍是 16 應該是 32，這個 bug 被我自己從「玩家卡在格邊」反推才發現——他沒有在自己的模組測試裡覆蓋到實際位移半徑；同樣地，store 的 pick 全排除時曾有 fallback 到全詞庫的問題，是 Codex 的契約測試抓到而不是他的。可改進處是「模組自測要包含與遊戲位移半徑的整合斷言」。建議職位：模組層與資料層負責人，維護成本最低。

[三] 我的失誤與下次改法

我的失誤集中在三類。第一是算術與語意：我在報告裡把「19 weapon + 6–8 被動」寫成 Lv20，又把「25 次升級」寫成 Lv25，都是少算 1；更嚴重的是我用這個錯誤前提去反推「4 MAX 是 Lv20 專家上限」，等於用錯證據擋了 Codex 的 cap90 提案。改法：任何「N 次選擇 = 等級 X」的換算，先用 config 跑一次數字再寫進結論。

第二是 fixture 缺陷被誤當成程式缺陷。我多次把「我的 helper 用 r=16 探測、遊戲用 r=18 判定」造成的卡死，寫成「seed12 路線不可通行」；把「update 在非 play 時 return 所以冷卻不減」寫成「while 迴圈無限循環」，而真正的機制是沙箱 performance.now() 恆為 0 導致 dt=0。改法：回報失敗時必須先寫「我預期什麼、實際什麼、差異是否來自我的探針」，並且優先寫最小重現腳本而不是直接下結論。

第三是我自己寫過假綠測試。`passive>=0`、`assert(null,null)` 的 12 單占位測試，都是形式上綠、實質上沒驗到東西；我還寫過 `assert.ok(true)` 的佔位測試。改法：新增測試時，標題寫的規則必須等於斷言檢查的東西，不等就寧可先不寫。

[四] 下次四人分工與協作規則

分工建議：Codex 負責整合與放行、Grok 負責單一大型 gameplay 檔、AGY 負責模組與資料層、我負責驗收工具與獨立複核。這個分法的好處是每份責任對應一種可驗證的產出，而不是對應一種能力。

協作規則我建議五條。第一，每份責任檔清單要寫在檔案裡，不靠記憶——這次 Codex 與 AGY 的檔案邊界中途調整過兩次，若無明文就會互相覆寫。第二，TDD 的 RED 必須由「非作者」執行，作者自測不算 RED；這次如果 Grok 或 AGY 自己驗自己的 RED，我很可能發現不了他們探針與實作同時錯掉的問題。第三，量測工具與被測程式要分開 hash 記錄，我的 baseline 測試固定讀 git show da98b4b 就是這個目的。第四，任何「存活」不得寫成「通過」，勝利要有終王死亡與達標配送兩個條件，這條我到第四輪才寫進報告。第五，每輪結束前作者必須自己先跑舊回歸並逐條分類是「意圖變更」還是「真 regression」，不能把舊斷言失敗籠統稱為預期變更。

最後一點：這次最有價值的產物不是任何一份測試，而是把「驗收數字如何得來」寫清楚到別人能重現。任何只給結論不給來源的驗收，都應該被退回。
